# Beam Cloud — Studio & Crew

This is the Render-ready web edition of Beam. The Windows desktop entry point, installer sources and existing releases are retained. `cloud_app.py` is the web entry point; `desktop.py` remains the desktop entry point.

## 1. Put the source in a GitHub repository

Unzip the Beam Cloud release and upload the files to a new GitHub repository. Keep `render.yaml`, `Dockerfile`, `cloud_app.py` and `requirements-cloud.txt` at the repository root. A private repository is fine. Do not upload API keys, Codespace data folders or local app data. The release ZIP contains source only.

## 2. Register GitHub sign-in

In GitHub, open **Settings → Developer settings → OAuth Apps → New OAuth App**.

- Application name: `Beam Cloud`.
- Homepage URL: the address you intend to use on Render, for example `https://your-beam-cloud.onrender.com`.
- Authorization callback URL: that address followed by `/auth/callback`.
- Copy the Client ID. Generate a client secret and keep it private.

If you do not know the Render address yet, register with a placeholder and edit both URLs once Render gives you the final address. GitHub sign-in uses OAuth directly; there is no paid identity-provider subscription and no Beam password database. Beam requests `read:user` and `codespace` access. It does not request Gists or general repository OAuth scopes.

GitHub guide: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/creating-an-oauth-app

## 3. Create the Render service

In Render choose **New → Blueprint**, connect the repository and select `render.yaml`. The Blueprint creates one **Free Docker web service**.

Set these environment variables when prompted:

| Variable | Value |
| --- | --- |
| `GITHUB_CLIENT_ID` | The GitHub OAuth Client ID |
| `GITHUB_CLIENT_SECRET` | The GitHub OAuth client secret |
| `BEAM_SESSION_KEY` | Generated by the Blueprint; retain this value between deployments |

If creating a Web Service manually, select **Docker**, the **Free** instance, `/healthz` as the health check and add the same variables. Set `BEAM_SESSION_KEY` to at least 32 cryptographically random characters. Do not put it in the repository.

Render provides `RENDER_EXTERNAL_URL` automatically. With a custom domain, set `PUBLIC_URL` to the exact public HTTPS origin, with no trailing path. Update the GitHub homepage and callback to the final address. Keep Render's default Docker start command; the image reads `PORT` automatically.

The Render service needs no shared Ollama key, persistent disk or database. Its dependencies are deliberately small; document, 3D, browser and MCP libraries install in the user's Codespace.

## 4. Connect a user's Codespace

1. Open Beam Cloud and choose **Continue with GitHub**.
2. Approve access, select a Codespace owned by that account and choose **Connect Codespace**.
3. On the first connection, Beam starts the Codespace and installs its private worker, generation libraries and headless Chromium. Allow several minutes. Setup requires a standard Linux Codespace with Python 3, SSH and passwordless sudo; custom containers may need adjustment.
4. Choose **Open project** to browse existing repository folders under `/workspaces`, or use **Beam workspace** to create a separate project folder.
5. In Settings, enter that user's Ollama Cloud API key and test the connection. The key is encrypted in the Codespace, not saved to a Gist or returned to the page.
6. Use **Studio** for personal sessions and **Crew** for the user's private team. Existing effort, approval, file preview, generation, avatar, role and memory controls remain available.

There are no commands to run on the user's PC. An SSH helper runs inside Render to relay requests. Project commands, file editing, browser automation, MCP processes and generation execute in the selected Codespace.

## 5. Leaving and background work

**Allow background work** is off by default. When no browser tab has checked in for two minutes, the Codespace worker saves resumable Studio/Crew records, cancels active work, closes development servers and asks GitHub to stop the whole Codespace. Other processes on that same machine also stop. Multiple connected Beam tabs are counted separately.

Use **Leave → Pause tasks & stop Codespace** for an immediate deliberate departure. Turn on **Settings → Allow background work** to permit the alternative **Continue in background**. Questions, approvals and privacy checkpoints still wait for user input. GitHub's idle timeout, maximum session length, usage allowance and token revocation can interrupt background work regardless of Beam's setting. Beam does not manufacture activity to evade provider limits.

Browsers allow a standard confirmation when the tab close button is used, not an app-defined dialog with custom choices. They may omit even that warning on mobile or after a crash. The independent Codespace watchdog covers unexpected loss of the browser/Render connection; it does not depend on Render staying awake. A disconnected or suspended browser can be treated as absent. Enable background work when ongoing execution is desired.

After reconnecting, open the **Codespace** button to resume saved tasks. Resuming continues from conversations and existing files; an interrupted shell command is not an operating-system snapshot and is not blindly replayed.

## Where information lives

| Information | Location |
| --- | --- |
| Studio messages, task events, Crew profiles/avatars/memory/briefs, paused task records and drafts | `/workspaces/.beam-cloud/beam.sqlite3` in that Codespace |
| Ollama and integration credentials | Encrypted files in `/workspaces/.beam-cloud`, using its private `vault.key` |
| Account ownership binding | `/workspaces/.beam-cloud/owner.json` |
| Project files and generated artifacts | The selected project folder under `/workspaces` |
| Worker environment | `/workspaces/.beam-cloud-runtime/<bundle-hash>/` |
| GitHub browser session | Encrypted, HttpOnly browser cookie; transient SSH connection state on Render |

No Gists are created. There are no public worker ports. Each worker is bound to a GitHub numeric account ID and reached through that account's authenticated Codespace SSH connection. The gateway verifies Codespace ownership; one account cannot select another account's Codespace. The application operator still handles authenticated relay traffic; this is not end-to-end encryption against the Render host.

The worker process and authorized project commands use the user's Codespace permissions. Codespaces are not separate security sandboxes for each bot. Keep unrelated secrets off a workspace used for autonomous commands. Pattern-based privacy checks pause before detected sensitive details go to Ollama Cloud; they do not detect every possible secret. There is no local Ollama option in this edition.

Deleting the Codespace deletes its uncommitted files and Beam database. Stopping it preserves them. Keep project code committed/backed up as usual. Desktop/cloud synchronization is not implemented yet; the cloud uses the same underlying message, event and Crew table formats to support that later work. Previous desktop Cloud Crew data in `.beam-crew` is retained separately and is not silently overwritten or migrated.

## Browser, Google and MCP

The **Browser** panel runs headless Chromium in the Codespace. Its page images, extracted controls, click/fill actions, persistent profile and downloads remain available. The desktop-only visible-window toggle is hidden. Google or other sites may restrict automated sign-in.

For Drive/Slides, create a Google OAuth **Web application** client, enable the Drive and Slides APIs, and register `https://YOUR-BEAM-URL/auth/google/callback` as its authorized redirect URI. Import that Web client JSON in Beam's Google connection controls and complete Google sign-in. Credentials and tokens stay in the Codespace. Desktop OAuth client JSON is not suitable for this web edition. Your Google consent screen and test-user configuration determine which accounts may connect.

MCP retains both Streamable HTTP and stdio support. Stdio commands run in the Codespace and require the relevant programs/packages to be available there. Bearer tokens and environment secrets use the Codespace vault. Development servers also run there; use GitHub's Codespace port-forwarding UI if you need a live public browser preview.

## Free Render constraints and troubleshooting

- Render Free sleeps after 15 minutes without inbound traffic and can restart at any time. Opening Beam may show Render's startup page for about a minute. Saved work remains on the Codespace, and enabled background work continues there while GitHub keeps it running.
- Free Render has resource, outbound-traffic and monthly usage limits. This lightweight gateway limits itself to four live SSH connections; evicted connections reconnect on demand without terminating worker jobs. This edition is intended for a small hobby deployment, not unlimited concurrent users.
- A changed `BEAM_SESSION_KEY` logs everyone out. It does not delete their Codespace databases or keys.
- A revoked/expired GitHub connection may prevent the worker from stopping the Codespace. Tasks are still cancelled and saved; Beam retries shutdown. GitHub's own limits remain in effect. Reconnect or stop the machine from GitHub if necessary.
- Worker setup failure: check that the Codespace has storage, Python 3/venv, network package access and passwordless sudo. Choose Connect again. No project command falls back to the user's PC or Render.
- For custom domains, callback and `PUBLIC_URL` mismatches cause sign-in or CSRF failures. Use the exact same HTTPS origin everywhere.

Render limits: https://render.com/docs/free
